Answers and Explanation

Q1. Looking at the backtrace output, which function called syscall()?

The backtrace showed:
- Frame 0: syscall(), the current function where execution was paused.
- Frame 1: 0x0000000080001b18 in usertrap() at kernel/trap.c:68, identifying the caller of syscall().
- Frame 2: 0x0000003ffffff09c in ?? (). GDB could not identify the function at this frame; unwinding across the trap boundary may be limited.

The user program requests a system call using the ecall instruction. The trap-entry code transfers control to usertrap(), which calls syscall() to dispatch the request to the appropriate handler.

Therefore, the function that called syscall() was usertrap(), at line 68 of kernel/trap.c in this build.

Q2. What is the value of p->trapframe->a7, and what does it represent?

The observed value of p->trapframe->a7 was 15. The process name was "init", and its PID was 1. In kernel/syscall.h, SYS_open is defined as 15.

The assignment’s hint refers to user/initcode.S, which is absent from the xv6 version used here. In this version, forkret() in kernel/proc.c calls kexec("/init", ...) directly. The first system call made by the resulting init program is open("console", O_RDWR) in user/init.c. This explains why the observed system-call number is SYS_open = 15, rather than SYS_exec = 7 as in versions that start user execution through initcode.S.

Therefore, the captured request was the open system call. The saved a7 register contains the system-call number, which the kernel uses to select the appropriate handler.

Q3. What was the previous mode that the CPU was in?

The observed value of sstatus was 0x200000022. The SPP bit, at bit position 8, was zero, indicating that the previous privilege mode was User mode.

The user process executed ecall, causing the CPU to trap into Supervisor mode to handle the system call. Thus, the CPU was previously in User mode.

Q4. Write down the assembly instruction the kernel is panicking at. Which register corresponds to the variable num?

The panic reported sepc = 0x80001d6e. The instruction at this address in kernel/kernel.asm was:

lw a3,0(zero)

This instruction corresponds to the injected C statement:

num = *(int *)0;

It attempts to load a 32-bit word from address zero into register a3. Therefore, a3 is the destination register corresponding to num at this instruction in this build.

Q5. Why does the kernel crash?

The panic output reported:
- scause = 0xd (13), indicating a load page fault.
- stval = 0x0, identifying the faulting virtual address.
- sepc = 0x80001d6e, identifying the instruction lw a3,0(zero).

The statement num = *(int *)0; attempts to read from virtual address zero, which is not mapped in the kernel page table. This causes a load page fault, with stval = 0 identifying the invalid address.

Since this fault occurs in the kernel and is not recovered from, kerneltrap() calls panic().

Q6. What is the name of the process that was running when the kernel panicked? What is its process ID?

GDB stopped at 0x80001d6e, with the program counter pointing to the faulting instruction lw a3,0(zero). The breakpoint stopped execution before that instruction executed.

Inspecting p->name and p->pid showed:
- Process name: "init".
- Process ID: 1.

Therefore, the process running when the kernel panicked was init, with PID 1.
